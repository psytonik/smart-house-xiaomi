# ADR 0003. Фильтр смены освещения, лимит диска и адрес по умолчанию

Дата: 2026-10-30. Статус: принято.

## Контекст

1. **Ложные клипы ночью.** Детектор движения считает долю изменившихся пикселей по всему кадру. Когда камера переключает ИК-фильтр (день и ночь) или резко меняется экспозиция, меняется почти весь кадр, и экспозиция ещё несколько кадров «плывёт». Такие моменты записывались как события.
2. **Диск ограничен только временем.** Клипы чистились по возрасту (`RETENTION_DAYS`). При частом движении диск мог заполниться раньше семи дней, а проверить занятое место через API было нельзя.
3. **Слушаем всех по умолчанию.** `HOST` по умолчанию был `0.0.0.0`: бэкенд без TLS открывался для всей сети, даже если владелец об этом не просил.

## Решение

### Фильтр смены освещения (`src/motion.ts`)

Кадр, где изменилось не меньше `MOTION_LIGHT_CHANGE` (60 %) пикселей, считается сменой освещения. Трекер не засчитывает его как движение и игнорирует `settleMs` (2 с) после него, пока картинка устаканится. Используется уже существующий механизм подавления движения после команд PTZ, поэтому новой машины состояний нет.

- Скачок во время идущего события не продлевает его и не попадает в `peak`.
- Кадр чуть ниже порога остаётся движением. Человек вплотную к камере обычно даёт 20–50 % изменения.
- Вся логика работает по соотношениям пикселей, моделей и OpenCV не нужно. Подход выбран как самый дешёвый для 4 кадров в секунду на кадре 320×180.
- Конфигурация проверяется при старте: `MOTION_LIGHT_CHANGE` должен быть больше `MOTION_THRESHOLD`, иначе никакое движение никогда не засчитывалось бы.

### Лимит размера (`src/events.ts`, `src/recorder.ts`)

- `MAX_STORAGE_GB` (по умолчанию 20). Если клипы занимают больше, удаляются самые старые, пока всё не поместится. **Самый новый клип остаётся всегда**, даже если он один больше лимита: только что записанное событие не должно исчезать.
- Проверка после каждого нового клипа и раз в 30 минут вместе с очисткой по возрасту.
- Размер считается по полю `bytes` в метаданных клипа (видео). Превью занимают килобайты и не учитываются.

### Состояние диска в `/api/status`

В ответ добавлено поле `storage`: `clips`, `usedBytes`, `limitBytes`, `freeBytes` (свободное место тома с данными по `statfs`). Результат кэшируется на 15 секунд, потому что веб-приложение опрашивает статус каждые 5 секунд, а подсчёт читает метаданные всех клипов. Кэш сбрасывается при новом клипе и удалении.

### `HOST=127.0.0.1` по умолчанию

Без явной настройки бэкенд доступен только с этого Mac. Чтобы открыть его для телефона в домашней сети, в `.env` нужно поставить `HOST=0.0.0.0`; для доступа через VPN указывается адрес Tailscale. Существующий `.env` с явным `HOST` не меняется и продолжает работать как раньше.

## Последствия

- Минус: если человек вплотную закрывает больше 60 % кадра, моментальный скачок будет пропущен как смена освещения, а события начнутся после 2 секунд. Порог настраивается.
- Минус: лимит диска хранит метаданные по клипам без индекса. На сотни клипов это дёшево, на тысячи стоит завести индекс (связано с пунктом «События в реальном времени» в роадмапе).
- Минус: смена `HOST` по умолчанию ломает запуск без `.env`, если кто-то рассчитывал на доступ с другого устройства. Поведение описано в README и `.env.example`.
- Не сделано: порог свободного места на диске (останавливать запись, если осталось меньше N ГБ). `freeBytes` для этого уже есть в API.
